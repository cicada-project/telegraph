# ADR 0006 — Client secure-state journal and audit chain

## Status

**Proposed — pending independent security review.**

This ADR narrows two persistence details left open by ADR 0002: protection of
the crash-recovery transition journal and construction of the local audit
chain. It is not implementation authorization, a release decision, or a
security certification. It does not change the selected Olm profile, create an
alternative transport cryptosystem, or establish that Telegraph implements
E2EE. T3b, T0 integration, provider/dependency closure, the R4 vectors, release,
and deployment remain separately gated.

## 1. Context and problem

ADR 0002 requires a single-writer, DB-first transition:

1. SQLite durably stores the complete target secure state and a `PREPARED`
   transition journal;
2. the client compare-and-swaps the independent external rollback anchor from
   the exact old generation/digest to the exact target generation/digest; and
3. SQLite changes only the journal status to `ANCHORED` and durably commits it.

The transition journal is excluded from `secure_state` and therefore from
`state_digest`. That exclusion is necessary: changing `PREPARED` to `ANCHORED`
must not require another anchor transition. It also means that the old external
anchor cannot authenticate an unprotected target journal in the crash state
where SQLite already contains the target but the anchor still contains the old
generation. A journal HMAC stored only in SQLite is also insufficient against
the stated WAL/page attacker: before the anchor changes, the daemon could have
legitimately produced two different tagged targets from the same old anchor,
or an old tagged `PREPARED` page could be revived after cancellation. Recovery
therefore needs a protected, durable, single-consumption commitment outside
SQLite that names the only currently authorized transition.

The accepted crypto core currently supports storage-record AAD kinds
`account`, `session`, `channel`, `dedup`, and `prekey`. It has no journal record
kind. Reusing one of those names for a transition journal would violate the
reviewed type/AAD boundary. Adding a new record kind is possible only through a
reviewed API/schema change.

ADR 0002 also names an `audit_chain_record`, but does not fix the entry MAC,
entry schema, compaction linkage, or privacy boundary. Those details must be
fixed before T3b can use audit state as an anchored security input.

## 2. Threat model and assumptions

### 2.1 In-scope attackers and failures

The design must fail closed under:

- a local attacker or faulty backup tool that can read, replace, delete,
  reorder, truncate, or restore SQLite database pages, committed WAL frames,
  uncommitted WAL frames, shared-memory bookkeeping, and stale page images but
  cannot read or modify the independently protected anchor and pending files;
- resurrection of a valid old `PREPARED` journal/page after its external
  pending authorization was aborted, consumed, or cleared;
- two different journal HMACs legitimately produced from the same
  `from_generation/from_state_digest`, only one of which may remain externally
  authorized;
- restoration of a complete older SQLite snapshot while the external anchor
  remains current;
- corruption or substitution of journal fields, encrypted-record metadata,
  audit rows, audit order, or compaction metadata;
- a crash or power loss before or after every SQLite commit, file fsync,
  external-anchor CAS, atomic rename, parent-directory fsync, and journal
  cleanup;
- accidental nonce reuse, record-version regression, generation overflow,
  storage-key loss, anchor unavailability, and a second writer;
- an unprivileged local process racing the dedicated daemon for the anchor
  lock or protected files.

### 2.2 Required assumptions

- `K_storage_master` and `K_anchor` are independent random 32-byte keys
  generated by the OS CSPRNG and stored outside the SQLite directory.
- The authenticated external anchor-state file and external pending-transition
  slot are also outside the SQLite directory and excluded from database
  backups. Both use the same stable lock inode and protected atomic-file update
  contract; neither is writable by the SQLite/WAL attacker.
- The Linux MVP enforces the protected-file owner, mode, no-symlink, stable
  lock-inode, fsync, rename, and directory-fsync contract from ADR 0004.
- One daemon writer owns the SQLite writer and external-anchor lock.
- HMAC-SHA-256, SHA-256, XChaCha20-Poly1305, and the existing record-AEAD
  construction behave as specified by their reviewed dependencies.
- The secure-state canonical encoder is exact, bounded RFC 8949 deterministic
  CBOR and rejects unknown, duplicate, reordered, indefinite, non-shortest, or
  trailing input.

### 2.3 Explicitly out of scope

This design cannot detect a simultaneous coordinated rollback of SQLite, the
external anchor, and the external pending-transition slot to mutually matching
authentic old values. It also
does not protect against a compromised root process or endpoint that can read
both protected keys and SQLite, an attacker controlling plaintext before
encryption or after handoff, denial of service, traffic analysis, or relay
metadata correlation. Such an event is endpoint compromise and requires device
recovery/re-pair; it must never be presented as detected by this design.

## 3. Journal alternatives

### 3.1 Alternative A — dedicated record-AEAD journal kind

Add `SecureTransitionJournal` to the crypto core's `RecordType`, derive a
record key through the existing HKDF construction, and store the canonical
journal as XChaCha20-Poly1305 ciphertext with the existing AAD fields:

```text
record_type    = "secure_transition_journal"
record_id      = device_id (bstr16)
record_schema  = 1
record_version = to_generation
```

Advantages:

- reuses the reviewed record AEAD and makes journal contents confidential and
  authenticated;
- uses the same strict envelope and AAD validation as other encrypted client
  records; and
- provides a natural fatal duplicate-nonce check.

Disadvantages:

- journal fields are not secret, so confidentiality has no identified benefit;
- it expands the accepted crypto API, record-type enum, migration rules, and
  independent-review surface;
- it adds a random 24-byte nonce, a 16-byte tag, nonce/version uniqueness state,
  and a second encrypted record write to every secure-state transition;
- most importantly, it couples recovery of the transition coordinating a
  `K_storage_master` rotation to whichever old/new storage key can open the
  journal. An interrupted key rotation would need an additional dual-key
  bootstrap rule before the journal used to resolve the rotation could itself
  be trusted; and
- loss of `K_storage_master` would make both encrypted state and the recovery
  journal unavailable, reducing diagnostic separation without improving the
  required fail-closed result.

Alternative A remains a possible future design, but is not recommended for the
MVP. It must not be implemented by borrowing `channel`, `dedup`, or another
existing record type.

### 3.2 Alternative B0 — plain metadata authenticated only after anchor match

Store the non-secret journal fields as canonical SQLite columns/CBOR and trust
them only by comparing the target digest with the external anchor.

This is adequate only after the external anchor already equals the target. It
is inadequate for the mandatory crash state `anchor=old, journal=PREPARED`,
because a SQLite-only attacker can replace the target state and the unkeyed
journal before the daemon retries the CAS. The old anchor authenticates only
the old digest, not the proposed target. An unkeyed hash of the journal does not
fix this because the attacker can recompute it.

Alternative B0 is rejected.

### 3.3 Alternative B1 — tagged metadata plus an external pending commitment

Store the exact non-secret journal fields in SQLite and authenticate them with
a domain-separated HMAC generated and verified inside the protected-state
adapter. Before SQLite writes any target pages, reserve one authenticated,
durable pending-transition slot outside SQLite. The slot binds the exact old
and target generations/digests plus a monotonically unique `transition_id`.
The adapter permits only one reserved transition. After the same live process
has observed a successful commit and durable target reopen it advances the slot
to `DB_COMMITTED`; the anchor CAS requires that exact state. The adapter exposes
typed reserve, durable-commit mark, verify, consume, abort, and clear
operations; it exposes neither raw `K_anchor` nor an arbitrary MAC function.

Advantages:

- authenticates the target while the external anchor is still old;
- makes the protected pending slot, rather than whichever tagged page SQLite
  presents, the single source of transition authorization;
- rejects a second target from the same old anchor while another target is
  reserved, and rejects old pages after the prior reservation is consumed or
  cleared;
- needs no new crypto record type, no journal nonce, and no new key;
- remains readable when `K_storage_master` is unavailable because it uses the
  independently protected anchor capability;
- uses the already selected HMAC-SHA-256 primitive and protected anchor key;
- is one small fixed record and two bounded HMAC operations per transition;
  and
- preserves the exact DB-first/CAS/ANCHORED recovery model.

Costs and limits:

- journal and pending-slot integrity now depend on `K_anchor`; compromise of that key is
  endpoint compromise;
- HMAC does not hide journal metadata, which is acceptable because the schema
  contains only generations, state digests, and status; and
- the protected adapter becomes a larger state machine and bounded MAC oracle.
  Its API must accept only the exact typed journal, anchor, and pending schemas,
  not arbitrary caller bytes or arbitrary domains; and
- each secure-state transition adds one protected pending reserve, one consume,
  and one clear in addition to the existing anchor CAS. These are small fixed
  file operations and buy protection that a SQLite-resident HMAC alone cannot
  provide.

### 3.4 Proposed journal decision

Select **Alternative B1** for independent security review. It is the lightest
option that both authenticates the pre-CAS target and makes that target a
single-use external authorization while avoiding a storage-key-rotation cycle.
B0 and a SQLite-only journal HMAC are not safe enough for the WAL/page attacker;
A adds AEAD state and recovery complexity without a confidentiality requirement.

## 4. Exact pending and journal profiles

### 4.1 External pending-transition slot

The protected backend maintains exactly one fixed-width pending slot per
device, next to but separate from the anchor-state file and outside the SQLite
directory. The exact ASCII HMAC domain is:

```text
PENDING_MAC = "telegraph/external-pending-transition/v1"
```

The file is exactly 160 bytes, with all integers unsigned big-endian:

| Offset | Bytes | Field | Exact rule |
|---:|---:|---|---|
| 0 | 8 | `magic` | ASCII exactly `TGPND001` |
| 8 | 8 | `slot_schema` | uint64 exactly `1` |
| 16 | 8 | `slot_sequence` | uint64, monotonically increases on every reserve |
| 24 | 1 | `slot_state` | `0=EMPTY`, `1=RESERVED`, `2=DB_COMMITTED`, `3=CONSUMED`, `4=CLEARED` |
| 25 | 7 | `reserved` | all zero; any nonzero byte rejects |
| 32 | 16 | `transition_id` | exact unique ID defined below |
| 48 | 8 | `from_generation` | uint64 |
| 56 | 32 | `from_state_digest` | exact SHA-256 digest |
| 88 | 8 | `to_generation` | checked `from_generation+1` |
| 96 | 32 | `target_state_digest` | exact SHA-256 digest |
| 128 | 32 | `pending_tag` | HMAC-SHA-256 over domain plus bytes `0..127` |

```text
pending_tag = HMAC-SHA-256(
  K_anchor,
  PENDING_MAC || pending_file_bytes[0..128]
)
```

The genesis `EMPTY` slot has sequence zero and all transition fields zero. A
successful or aborted clear writes `CLEARED`, retains the last transition
binding, and retains its `slot_sequence`; it never returns to `EMPTY`. A new
reservation performs checked `slot_sequence+1` and defines:

```text
transition_id = uint64_be(slot_sequence) || os_csprng_random_8
```

The first eight ID bytes must equal the stored slot sequence, the random suffix
must not be all zero, and the complete ID must differ from the retained prior
ID. Sequence overflow or CSPRNG failure is fatal. Thus two aborted attempts
from the same anchor have different durable IDs, and an old tagged SQLite page
is rejected after the external slot advances or clears.

Every slot update holds the stable external lock, validates the current anchor
and slot HMACs, writes a same-directory root-owned mode-0600 temporary file,
fsyncs it, atomically renames it, fsyncs the parent directory, and reopens and
verifies the exact result. A crash yields the complete old or complete new
valid slot; a partial or malformed file fails closed. The pending file is never
included in a SQLite backup.

The slot state transitions are closed:

```text
EMPTY        -> RESERVED
CLEARED      -> RESERVED
RESERVED     -> DB_COMMITTED  # live normal flow only after durable target verification
RESERVED     -> CLEARED       # abort only while anchor/SQLite are exact from-state, no journal
DB_COMMITTED -> CONSUMED      # only after exact anchor CAS reached target
CONSUMED     -> CLEARED       # only after SQLite journal is durably ANCHORED
```

Every other transition rejects. `reserve` refuses a second target while the
slot is `RESERVED`, `DB_COMMITTED`, or `CONSUMED`. `mark_db_committed` is an
external compare-and-swap over the complete exact `RESERVED` slot and requires
both an in-memory, non-serializable live-reservation capability and a durable
target proof produced by the same normal execution flow. That proof exists
only after SQLite commit returned success, a separate durable reopen observed
the commit, and target state plus tagged journal were recomputed byte-exact.
Startup/recovery receives neither capability and **must never** change
`RESERVED` to `DB_COMMITTED`.

The external anchor CAS accepts only the exact current `DB_COMMITTED` slot.
`consume` requires that slot and the exact target anchor. `clear` is a
compare-and-swap over slot sequence, state, ID, and all generation/digest
fields. Clearing never authorizes an old journal: recovery of a SQLite
`PREPARED` row requires the current external slot to be `DB_COMMITTED` or
`CONSUMED` with a byte-exact binding. If SQLite really committed but the process
crashed before `DB_COMMITTED` became durable, startup sacrifices availability
and fail-stops; it does not infer or recreate the missing authorization from
SQLite, WAL, or a valid journal tag.

### 4.2 SQLite journal domain and canonical schema

The exact ASCII domain is:

```text
JOURNAL_MAC = "telegraph/secure-transition-journal-mac/v1"
```

There is no NUL, length prefix, implicit separator, alternate spelling, or
caller-supplied domain. The deterministic-CBOR map without the tag has exactly
keys `0..7`:

| Key | Field | Exact type and rule |
|---:|---|---|
| 0 | `journal_schema` | uint exactly `1` |
| 1 | `pending_slot_sequence` | uint64, equals external slot sequence |
| 2 | `transition_id` | bstr exactly 16, equals external slot ID |
| 3 | `from_generation` | uint64 |
| 4 | `from_state_digest` | bstr exactly 32 |
| 5 | `to_generation` | uint64, exactly `from_generation + 1` |
| 6 | `target_state_digest` | bstr exactly 32 |
| 7 | `status` | uint exactly `0=PREPARED` or `1=ANCHORED` |

The stored journal is the same map plus key `8`:

| Key | Field | Exact type and rule |
|---:|---|---|
| 8 | `journal_tag` | bstr exactly 32 |

```text
journal_tag = HMAC-SHA-256(
  K_anchor,
  JOURNAL_MAC || deterministic_cbor(map keys 0..7)
)
```

The complete stored journal is at most 320 bytes. Definite map length, sorted
integer keys, shortest unsigned integers, exact byte lengths, exact key set,
and byte-equal schema-specific re-encoding are mandatory. Tags, floats,
negative integers, `undefined`, indefinite items, duplicate/unknown keys, and
trailing bytes reject before any recovery action.

Changing `PREPARED` to `ANCHORED` recomputes key `8` over the new status. The
journal itself, including its tag and status, remains excluded from
`secure_state`, `state_digest`, and the audit-chain head.

### 4.3 Required transition invariants

- `to_generation` must equal checked `from_generation + 1`; u64 overflow is
  fatal.
- `from_generation/from_state_digest` must equal the exact expected external
  anchor value used for CAS.
- `target_state_digest` must equal a fresh canonical recomputation from the
  complete target SQLite secure state, not a cached caller claim.
- Journal keys `1..6` must byte-for-byte equal the current external pending
  slot binding. A valid journal tag without that current external reservation
  is not authorized recovery input.
- There is at most one journal row and one pending slot per device and one
  writer per device.
- Journal, pending, and anchor tags are verified in constant time before any
  CAS, status change, database repair, or output-eligibility decision.
- A journal from another device cannot be used because each device has an
  independent random `K_anchor`; journal rows contain no reusable global key.
- An invalid or absent tag is never repaired by computing a new tag over
  attacker-supplied fields.
- A second valid journal/tag from the same `from_*` is rejected unless its ID
  and slot sequence equal the one current pending slot. Only the live normal
  flow may move its own `RESERVED` binding to `DB_COMMITTED`; startup cannot do
  so. Clearing or consuming a different transition invalidates that journal. A
  matching `CONSUMED` slot can authorize only post-anchor completion; it can
  never authorize an anchor CAS.

## 5. DB-first transition and closed startup states

### 5.1 Normal transition

1. Acquire the SQLite single-writer guard and the stable protected-state file
   lock. Read and verify the current external anchor and pending-slot HMACs.
   The slot must be `EMPTY` or `CLEARED`. Before reserving, an exact retained
   `ANCHORED` journal from the preceding transition must pass state `R3b`
   and be durably cleaned; re-read proves no journal remains. Thus a new
   reservation never coexists with an older journal row.
2. Recompute and verify the current SQLite secure-state digest. It must equal
   the external anchor before a new transition starts. A mismatch enters the
   process-level fail-stop from section 5.3 and performs no SQLite write.
3. Construct the complete target secure state with checked generation `old+1`.
   Recompute `target_state_digest`; caller code does not generate or choose a
   transition ID.
4. Call the typed external `reserve_pending` CAS. It binds the exact old and
   target generation/digest and generates the next unique transition ID inside
   the protected adapter in one durable `RESERVED` slot. It returns a
   non-cloneable, non-serializable `LiveReservedPending` capability held only by
   this process execution.
   This reservation authorizes a target; it does not change the external
   anchor and is not a substitute for the DB-first state commit.
5. Inside SQLite transaction 1, write every target record, counter, dedup,
   receipt/handoff, audit, record index, storage generation, and exact tagged
   `PREPARED` journal. Commit with the required durable SQLite settings. No
   outbound send or local plaintext handoff becomes eligible yet.
6. In the same uninterrupted normal execution, close the transaction handle,
   durably reopen SQLite, and recompute the complete target and tagged journal.
   `ClientStore::verify_durable_target` returns a non-serializable
   `DurableTargetProof` only after commit returned success and this reopen is
   byte-exact. It returns no proof for an ambiguous commit result.
7. Call `mark_db_committed(live_reservation, durable_target_proof)`. The
   protected adapter re-verifies the exact external binding and CASes
   `RESERVED` to durable `DB_COMMITTED`. Neither capability can be reconstructed
   by startup, decoded from SQLite, or persisted for later use.
8. Re-read the external slot, journal, and freshly recomputed SQLite target.
   The anchor CAS is enabled only if the current slot is the same exact
   `DB_COMMITTED` transition.
9. CAS the external anchor from the exact old generation/digest to the exact
   target generation/digest. A comparison mismatch is never merged.
10. Call `consume_pending`, CASing the exact `DB_COMMITTED` slot to `CONSUMED`
   only after the authenticated anchor is observed at the target.
11. Inside SQLite transaction 2, change only journal status/tag to `ANCHORED`
   and commit durably. Re-read and verify target SQLite, target anchor,
   `ANCHORED` journal, and matching `CONSUMED` slot.
12. Call `clear_consumed`, CASing the slot to `CLEARED` while retaining its
    sequence, transition ID, and binding; reopen and verify it.
13. Only after step 12 may the caller expose a prepared outbound envelope or a
    pending local handoff.

No SQLite transaction is held across the external file CAS. This is a
recoverable sequence, not an atomic multi-resource CAS. The secure-state
mutation remains DB-first: the pending reservation is authorization metadata,
while the anchor itself changes only after target SQLite is durable.

If execution fails after reserve but before SQLite transaction 1 commits, the
reservation may be aborted only after a fresh SQLite read proves the database
and visible WAL state are still exactly the authenticated from-state and no
journal exists, and the anchor is still exact from-state. `clear_aborted`
changes the exact `RESERVED` slot to `CLEARED`. If any fact is uncertain, the
process fail-stops without writing SQLite or clearing the reservation. After
transaction 1 commits there is no normal cancellation. If the process crashes,
or loses either live proof, before step 7 is durably verified, startup sees
`RESERVED` plus a visible target/journal and returns
`DB_COMMIT_AUTHORIZATION_MISSING`; it never upgrades that state. This deliberate
availability loss is required by the strong WAL/page attacker model.

### 5.2 Exact startup recovery

After verifying protected files and taking the single-writer lock, startup
matches exactly one row of this closed state matrix. `from` and `target` always
mean the exact authenticated values in the same pending/journal binding:

| State | SQLite/journal | Anchor | Pending | Only permitted startup action |
|---|---|---|---|---|
| `G0` | exact genesis/no journal | genesis | genesis `EMPTY` | stable; no write |
| `S0` | current/no journal | current | `CLEARED` whose retained `from` (aborted) or `target` (successful) equals current | stable; no write |
| `S0-clean` | current/`ANCHORED` | current | `CLEARED` whose retained `target` equals current and matches journal | verify, then optional journal cleanup |
| `A0` | from/no journal; uncommitted WAL remains invisible | from | exact `RESERVED` | prove exact from-state, then abort-clear |
| `F0` | visible target/`PREPARED` | from | exact `RESERVED` | `DB_COMMIT_AUTHORIZATION_MISSING`; process fail-stop, no upgrade |
| `R1` | target/`PREPARED` | from | exact `DB_COMMITTED` | retry exactly one anchor CAS, then consume/anchor/clear |
| `R2a` | target/`PREPARED` | target | exact `DB_COMMITTED` | no second anchor CAS; consume/anchor/clear |
| `R2b` | target/`PREPARED` | target | exact `CONSUMED` | mark `ANCHORED`, then clear |
| `R3a` | target/`ANCHORED` | target | exact `CONSUMED` | verify, then clear |
| `R3b` | target/`ANCHORED` | target | retained matching `CLEARED` | verify, then optional journal cleanup |

`F0` covers both a genuine SQLite commit followed by a crash before external
`DB_COMMITTED` and an attacker making formerly uncommitted WAL/pages appear as
a committed target. Startup cannot distinguish them and intentionally rejects
both. It does not call `mark_db_committed`, mint a live capability, retry the
SQLite commit, retag the journal, or perform the anchor CAS.

Every row requires canonical state recomputation, exact adjacent generations,
byte-equal journal/pending binding, and constant-time authentication. Any
combination not listed—including **every** `RESERVED` state with a visible
target or any journal, old SQLite with target anchor, same-generation changed
digest, missing journal while stores differ, invalid HMAC, non-adjacent
generation, multiple journals, `PREPARED` with `CLEARED`/other pending ID,
resurrected cancelled pages, malformed state, or an anchor unrelated to both
journal endpoints—enters process fail-stop before a database write, decrypt,
encrypt, send, or handoff.

An ambiguous CAS error is resolved only by re-reading the authenticated
external anchor. Code never infers success from an I/O error.

### 5.3 Process-level fail-stop and complete crash matrix

An anchor/SQLite/pending/journal mismatch makes the SQLite store untrusted.
Startup performs this comparison through a read-only, no-create verification
handle and does not enable the writer handle until the complete state is
accepted. The process records only an in-memory fail-stop reason and may emit a
fixed, redacted process diagnostic. It does **not** insert a quarantine row,
repair a journal, append a database audit event, checkpoint WAL, rewrite the
database/WAL/shared-memory files, or otherwise write the untrusted database.
Every crypto, send, receive, and handoff entry point returns the same
unavailable/repair-required class. Persistent quarantine is a future design and
is not simulated by writing to suspect SQLite.

The same closed matrix expressed by normal-path durable boundary is:

| Last durable boundary | SQLite/journal | Anchor | Pending slot | Recovery |
|---|---|---|---|---|
| before pending reserve | from/no journal | from | old `EMPTY/CLEARED` | ordinary retry |
| reserve complete, before DB commit | from/no journal, including ignored uncommitted WAL | from | exact `RESERVED` | prove exact from-state, then abort-clear |
| target DB commit or durable reopen, before pending mark | target/`PREPARED` | from | exact `RESERVED` | `F0`; process fail-stop, repair required |
| pending `DB_COMMITTED` mark | target/`PREPARED` | from | exact `DB_COMMITTED` | `R1` |
| anchor CAS | target/`PREPARED` | target | exact `DB_COMMITTED` | `R2a`; consume |
| pending consume | target/`PREPARED` | target | exact `CONSUMED` | `R2b`; mark journal |
| journal `ANCHORED` commit | target/`ANCHORED` | target | exact `CONSUMED` | `R3a`; clear |
| pending clear | target/`ANCHORED` | target | exact `CLEARED` | `R3b`; optional journal cleanup |
| journal cleanup | target/no journal | target | retained exact `CLEARED` | `S0`; stable |

For every external anchor or pending-file update, a crash before rename yields
the old valid file and a crash after rename yields the new valid file; temp-file
fsync, rename, directory-fsync, or reopen ambiguity is resolved by rereading
both authenticated external files. Any old/new combination not in the table
fail-stops. An independently rolled-back pending file that no longer agrees
with the current anchor/SQLite also fail-stops. Only a coordinated authentic
rollback of all three stores remains the explicit undetectable non-goal.

## 6. Journal lifecycle, nonce/version rules, and rotation

### 6.1 Journal cleanup

- A `PREPARED` journal is never deleted.
- After target anchor, target SQLite, matching `CONSUMED` slot, and `ANCHORED`
  journal have all been re-read and verified, the slot is first changed to
  retained `CLEARED`. A later bounded checkpoint may delete the journal row
  only while that exact cleared binding and exact target anchor remain current.
- A crash during cleanup therefore leaves either a valid `ANCHORED` row or no
  row with exactly matching SQLite/anchor/cleared-slot state; both are recovery
  state `R3b` or stable state `S0`.
- Historical journals are not retained in SQLite. Journal cleanup itself does
  not append a database audit entry because doing so would create another
  secure-state transition. Fixed protected-file diagnostics may report cleanup
  without state digests, aliases, IDs, or key material.
- Starting a later secure-state transition requires the preceding exact
  `ANCHORED` journal to be cleaned first. The subsequent external reservation
  is not permitted while any journal row remains.
- A `CLEARED` pending slot never validates a resurrected `PREPARED` journal,
  even if the journal HMAC is valid. A matching `CONSUMED` slot validates
  `PREPARED` only in recovery state `R2b`, where anchor and SQLite are already
  the exact target; recovery may only finish `ANCHORED` and clear, never CAS a
  new anchor target. Every other resurrected page enters process fail-stop
  rather than being retagged or deleted.

### 6.2 Storage-record nonce and version uniqueness

The selected HMAC journal has no nonce and is not a storage-record AEAD object.
All encrypted account/session/channel/dedup/prekey records retain ADR 0002's
rules:

- a fresh random 24-byte nonce for every record write;
- durable uniqueness of `(record_id, record_version, nonce)` enforced by a
  SQLite constraint and verified before commit;
- monotonically increasing checked record versions included in exact AAD and
  the anchored storage-record index;
- a collision or version regression returns `RECORD_NONCE_REUSE` or
  `STATE_INCONSISTENT`, enters process fail-stop, and is never hidden by
  retrying with a new nonce; and
- record type/id/schema/version, nonce, ciphertext/tag, blob digest, and
  storage-master generation are covered by the complete secure state.

### 6.3 No online key rotation in the lightweight MVP

This MVP does **not** implement online rotation of either `K_storage_master` or
`K_anchor`. The current schemas have no independently reviewed dual-key slot,
key-generation CAS, or interrupted dual-key recovery protocol. Implementing
one inside T3b would recreate the circular recovery problem this ADR avoids.

Any storage-key or anchor-key rotation request, suspected key compromise,
missing key, mixed key generation, or erase uncertainty returns the single
stable code `SECURE_STATE_REPAIR_REQUIRED`. The client performs no reseal,
dual-slot guess, database rewrite, or old-key deletion. It fail-stops the device
and requires provisioning a fresh secure store/device identity as applicable,
new channels, independent safety comparison, and re-pair. Existing protected
key files are retained for explicit operator recovery until the replacement is
complete; automated secure erase is not claimed.

A future online key-rotation design requires a new ADR, exact key-generation
schema, independent crash matrix, migration, and security review. The external
pending slot in this ADR is a transition authorization slot, not a key-rotation
dual slot.

## 7. Audit-chain alternatives

### 7.1 Keyed HMAC chain

Each bounded canonical event includes the previous event tag and is tagged with
HMAC-SHA-256 under `K_anchor` using an audit-only domain. The current head and
compaction watermark are included in canonical `secure_state` and therefore in
the external anchor.

Benefits are strong local tamper detection before and after the next anchor
transition, inability for a SQLite-only attacker to recompute a replacement
chain, and no extra key file or dependency. Domain separation and an adapter
API restricted to the exact audit schema prevent a general caller-controlled
MAC oracle.

HMAC does not encrypt audit metadata. Privacy still depends on the schema never
accepting plaintext, raw codes, real thread/workspace identifiers, keys, state
digests, or provider values.

### 7.2 Unkeyed SHA-256 chain plus anchored head

An unkeyed chain is simple and, once its final head is included in a matching
external anchor, detects many later modifications. Before anchoring, however,
a SQLite-only attacker can rewrite events and recompute the chain. It also
makes offline equality/dictionary checks against low-entropy event detail
easier. The transition-journal HMAC would eventually bind the target head, but
using an unkeyed audit chain creates two integrity models and weaker diagnostics
for little measurable performance benefit.

This alternative is not selected.

### 7.3 AEAD-encrypted audit rows

Encrypting every audit row would hide some local metadata but adds per-row
nonce/version state, storage-key-rotation work, and recovery complexity. It
does not permit plaintext, raw codes, or real thread IDs to be logged in the
first place. Confidential diagnostic logs also complicate operator inspection.

This alternative is deferred. Privacy-sensitive secret material is prohibited
from the audit schema rather than made acceptable by encryption.

### 7.4 Proposed audit decision

Select the keyed HMAC chain for independent review. Use `K_anchor` only through
a schema-restricted protected-adapter operation and a distinct exact domain.
Do not derive a new audit key or introduce a new credential file in the MVP.

## 8. Exact audit-chain profile

### 8.1 Domain and entry schema

The exact ASCII domain is:

```text
AUDIT_ENTRY_MAC = "telegraph/audit-chain-entry/v1"
```

The map authenticated by HMAC has exactly keys `0..11`:

| Key | Field | Exact type and privacy rule |
|---:|---|---|
| 0 | `audit_schema` | uint exactly `1` |
| 1 | `sequence` | uint64, starts at 1 and increases exactly by 1 |
| 2 | `previous_tag` | bstr exactly 32; all-zero only for sequence 1 |
| 3 | `anchor_generation` | uint64 target generation containing this event |
| 4 | `event_code` | one closed enum value from section 8.2 |
| 5 | `outcome_code` | one closed enum value from section 8.2 |
| 6 | `occurred_at` | uint64 UTC Unix epoch seconds, nondecreasing within the chain |
| 7 | `endpoint_audit_alias` | null or random bstr16 alias; never a protocol/local endpoint ID |
| 8 | `channel_audit_alias` | null or random bstr16 alias; never `channel_id` or its hash |
| 9 | `subject_audit_alias` | null or random bstr16 alias for a message/delivery/operation/prekey/pairing |
| 10 | `reserved` | uint exactly `0` |
| 11 | `detail_code` | one closed enum value from section 8.2; never free-form text |

The stored event adds exact key `12`:

| Key | Field | Exact type and rule |
|---:|---|---|
| 12 | `entry_tag` | bstr exactly 32 |

```text
entry_tag = HMAC-SHA-256(
  K_anchor,
  AUDIT_ENTRY_MAC || deterministic_cbor(map keys 0..11)
)
```

`previous_tag` is the immediately preceding stored or compacted event tag.
`audit_chain_record.chain_head_digest` is the latest `entry_tag`, not an
unkeyed digest. The fixed `audit_chain_record` remains the ADR 0002 map:

```text
{ 0: chain_schema=1,
  1: chain_head_digest=bstr32,
  2: compaction_watermark=uint64,
  3: last_generation=uint64 }
```

The exact empty-chain state at fresh generation zero is: no audit rows,
`chain_head_digest=32*0x00`, `compaction_watermark=0`, and
`last_generation=0`. For a non-empty chain, the final row's `entry_tag` equals
the head, its `anchor_generation` equals `last_generation`, and because every
secure-state generation emits at least one audit row, `last_generation` equals
the enclosing `secure_state.anchor_generation`. If rows remain after
compaction, the last remaining row must satisfy those invariants; if no rows
remain, the watermark identifies the last compacted sequence and the retained
head is the predecessor of the next event.

Each encoded audit event is at most 512 bytes. No strings, arbitrary blobs,
addresses, filenames, errors, stack traces, state digests, ciphertext
fingerprints, plaintext digests, device/user codes, public/private keys,
provider state, protocol IDs, local endpoint handles, or real Codex identifiers
are accepted by this schema.

### 8.3 Audit-alias lifecycle and collisions

An audit alias is a fresh random 16-byte value from the OS CSPRNG. It is not a
protocol ID, endpoint handle, channel/message/delivery ID, hash, truncated hash,
counter encoding, or encrypted real identifier.

The accepted crypto core currently keeps account bytes private in
`OpaqueAccountState` and `seal_account_state` only seals that opaque value; the
store cannot safely append a registry to the ciphertext or access provider
pickle bytes (`crates/crypto/src/account.rs:127-165` and
`crates/crypto/src/record.rs:225-246` at the stated source baseline). T3b
therefore requires a reviewed crypto-core internal account
payload version upgrade and typed registry codec/API. It does **not** add a
`RecordType`: the result remains one `RecordType::Account` envelope with the
existing record AAD construction. Account-v5 uses outer `record_schema=2`, an
initial `record_version=1` on fresh device creation, checked `record_version+1`
on every later Account write, and a fresh 24-byte nonce. Outer account schema 1
is legacy client input and is never reinterpreted as account-v5.

The exact fresh T3b account payload is internal version 5:

```text
account_v5 =
  magic "T3AS" (4) || version 5 (u8) ||
  provider_len (u32_be) || inventory_len (u32_be) || proof_len (u32_be) ||
  used_count (u16_be) || alias_registry_len (u32_be) ||
  structural_binding (bstr32) ||
  provider || inventory || proofs || used_wire_ids || alias_registry

  structural_binding = SHA-256(
  "telegraph/account-state-binding/v5" || version ||
  all encoded length/count fields ||
  provider || inventory || proofs || used_wire_ids || alias_registry
)
```

`used_wire_ids` is exactly `used_count * 16` bytes. The v5 plaintext is the
complete canonical byte sequence above, including every provider, inventory,
proof, used-ID, and alias-registry byte; there is no separately encrypted or
unbounded component budget. The existing crypto record plaintext hard cap is
the governing limit:

```text
MAX_ACCOUNT_V5_PLAINTEXT = MAX_RECORD_PLAINTEXT = 1_048_576
```

The name on the right denotes the existing crypto core's 1 MiB record
plaintext limit (currently enforced by its private record-size guard); this
ADR does not change that guard or add a larger `RecordType`.

The v5 decoder preserves the existing provider/inventory/proof/used bounds and
rejects wrong magic/version, checked-length overflow, trailing bytes, or a
binding mismatch. Version 4 or older inside a client database is legacy input
under section 10 and is not silently upgraded or resealed.

`alias_registry` has exact binary form:

```text
magic "T3AR" (4) || registry_version 1 (u8) || reserved_zero (3) ||
entry_count (u32_be) || entry_count * audit_alias_binding
```

Each `audit_alias_binding` is exactly 64 bytes:

| Offset | Bytes | Field | Exact rule |
|---:|---:|---|---|
| 0 | 1 | `binding_schema` | exactly `1` |
| 1 | 1 | `object_kind` | `1=ENDPOINT`, `2=CHANNEL`, `3=MESSAGE`, `4=DELIVERY`, `5=OPERATION`, `6=PREKEY`, `7=PAIRING`, `8=RECEIPT`, or `9=HANDOFF` |
| 2 | 1 | `lifecycle` | exactly `0=LIVE` or `1=TOMBSTONE` |
| 3 | 1 | `reserved0` | zero |
| 4 | 16 | `local_object_key` | exact private local/protocol object key |
| 20 | 16 | `audit_alias` | random bstr16 |
| 36 | 8 | `created_generation` | uint64 big-endian |
| 44 | 8 | `last_audit_sequence` | uint64 big-endian; zero means never emitted |
| 52 | 8 | `security_retention_until` | uint64 UTC epoch seconds |
| 60 | 4 | `reserved1` | all zero |

Entries are canonically sorted by numeric `object_kind`, then bytewise
`local_object_key`. That tuple and `audit_alias` are each unique across all
retained entries. The registry holds at most 10,000 entries and is at most
`12 + entry_count * 64` bytes. Thus the physical 10,000-entry registry is
`640,012` bytes, not an independent plaintext allowance and not a promise
that it fits beside an arbitrary provider state.

`AccountState` follows the existing crypto hard cap on plaintext record size
and therefore requires the complete canonical v5 byte sequence to satisfy:

```text
v5_fixed_len = 4 + 1 + 4 + 4 + 4 + 2 + 4 + 32 = 55
v5_variable_len =
  len(provider) + len(inventory) + len(proofs) +
  (used_count * 16) + len(alias_registry)
account_v5_len = v5_fixed_len + v5_variable_len

account_v5_len <= MAX_ACCOUNT_V5_PLAINTEXT = 1_048_576
v5_variable_len <= 1_048_521
len(alias_registry) <= min(
  640,012,
  1,048,521 - len(provider) - len(inventory) - len(proofs) - (used_count * 16)
)
```

All additions, multiplications, conversions, allocations, and the canonical
encoder's final length are checked before any registry mutation, alias
randomness, outer nonce, reseal, or call to `seal_account_state`. The maximum
10,000-entry registry consumes `640,012` bytes and therefore permits at most
`408,509` bytes for the other variable v5 components (the 55-byte framing is
already accounted for). The 10,000-alias objective is consequently limited to
states whose actual base payload plus registry satisfies this aggregate
formula; it is not guaranteed for a maximum-size provider/inventory/proof/
used-ID combination. Any standalone registry budget that exceeds the 1 MiB
complete-plaintext limit is invalid.

Preflight checks reject before any randomness, reseal, or mutation if:

- `entry_count > 10,000`,
- checked arithmetic, allocation, or canonical encoding of any component
  overflows, or
- the exact aggregate `account_v5_len` exceeds
  `MAX_ACCOUNT_V5_PLAINTEXT`.

For a target with 10,000 entries, success is possible only when the live base
payload plus registry fit under the aggregate cap. No claim is made that 10,000
aliases can coexist with any maximum-size base payload.

`AuditAliasBinding`, `AuditAliasRegistry`, `AuditAliasMutationBatch`, and
`ValidatedAuditAlias` have private fields. The crypto API provides only typed
`lookup`, `preflight_batch`, `apply_batch`, v5 decode/export, and provider-state
preserving update operations. It never exposes provider bytes, raw registry
bytes, an arbitrary account-payload encoder, or constructors that bypass
ordering/lifecycle validation. `DeviceAccount::from_state` and every account
export path must preserve the validated registry; a provider mutation cannot
drop or reset it.

Before drawing alias randomness or mutating state, `preflight_batch` validates
the current v5 payload, checks at most 16 alias mutations, exact target
count/size, every target provider/inventory/proof/used-ID/registry component,
the checked aggregate plaintext bound, checked outer Account record-version
increment, storage-index capacity, and memory allocation. A binding-count or
storage-index limit returns `AUDIT_ALIAS_CAPACITY_EXHAUSTED`; an arithmetic or
aggregate canonical-v5 size failure returns `ACCOUNT_V5_SIZE_EXCEEDED`.
Neither result consumes randomness or changes the account. After a valid alias
batch is built, the
ordinary record path draws one
fresh outer nonce and proves its durable tuple unique before commit; nonce
failure also leaves the old account unchanged. Each new candidate is checked
against all live entries, retained tombstones, and earlier candidates in the
batch. A collision discards it and retries at most 16 times per binding;
exhaustion
returns `RANDOMNESS_FAILURE` with no partial state.

A `LIVE` alias is created in the same target transition as its object, remains
stable for that object's lifetime, and is looked up without changing the
registry. Repeated audit events therefore do not update/reseal the Account
record merely to advance a sequence. In the transition that removes the
object, the entry becomes `TOMBSTONE`, `last_audit_sequence` is set to the last
event for that alias in that same transition, and
`security_retention_until` is set to the greatest applicable security
deadline; neither value may decrease. A tombstone may be deleted only when
`compaction_watermark >= last_audit_sequence`, trusted UTC is strictly greater
than `security_retention_until`, and every owning replay/receipt/prekey/pairing/
handoff/revocation relationship is legally removable. Otherwise deletion or
reuse is `STATE_INCONSISTENT`.

All alias changes in one secure-state transition are applied as one sorted
batch and cause at most one bounded account-v5 rebuild and one outer Account
reseal. Lookup-only audit events cause none. Tombstone cleanup removes at most
1,000 bindings in one maintenance transition. A new message that needs a new
alias may require one bounded reseal, never one reseal per audit event or an
unbounded full-registry operation. The daemon may cache a validated lookup
index, but restart must re-open the Account AEAD, validate v5 structural binding
and complete registry canonicality, and compare the anchored Account
digest/version before the cache is usable. Registry decode/rebuild/reseal at
the 10,000-entry cap is included in the section 12 p95 budget and requires a
dedicated maximum-size benchmark.

### 8.4 Audit behavior and compaction

- Audit insertion and the security-relevant state mutation occur in the same
  SQLite transaction and the resulting head is part of the target secure
  state.
- Event/tag failure aborts the state mutation. Security-relevant actions do not
  continue with an unaudited state.
- `occurred_at` is UTC Unix epoch seconds. Equal timestamps are allowed; a
  value lower than the previous entry is a trusted-clock rollback and aborts
  the transition. Time is not used as the chain order; `sequence` is.
- Sequence overflow is fatal and fail-stops; sequence gaps, duplicate rows,
  invalid tags, changed previous tags, deletion, insertion, reorder, fork, or
  a final head mismatch fail startup verification.
- At most 16 audit events may be emitted by one secure-state transition. More
  events fail the transition instead of allocating an unbounded batch.
- The live detailed ring is capped at 10,000 rows. One maintenance transition
  may compact at most 1,000 oldest rows.
- Compaction advances `compaction_watermark` to the last removed sequence but
  retains the current overall chain head. The first remaining row must have
  sequence `watermark+1`; its HMAC-authenticated `previous_tag` preserves the
  link to the compacted prefix. If all details are removed, the watermark is
  the last sequence and the retained chain head is used as the next event's
  `previous_tag`.
- Replay watermarks, receipt levels, invalid-auth budget, revocation state,
  quarantine state, storage-record index, and rollback-anchor fields are
  canonical secure state, not disposable audit detail, and cannot be removed
  by audit compaction.

The HMAC chain provides integrity against the stated SQLite-only attacker. It
does not make audit rows confidential and does not establish non-repudiation or
protection from a compromised endpoint holding `K_anchor`.

## 9. Failure codes and fail-closed outcomes

The following are stable local/internal classes. External APIs may collapse
them to a generic unavailable result and must not expose a state oracle.

| Code | Trigger | Required outcome |
|---|---|---|
| `JOURNAL_INVALID` | malformed, non-canonical, duplicate, missing, or impossible journal field | process fail-stop; no DB write |
| `JOURNAL_AUTH_FAILED` | journal HMAC mismatch | process fail-stop; no DB write |
| `JOURNAL_STATE_MISMATCH` | journal does not match recomputed SQLite/anchor/current pending slot | process fail-stop; no DB write |
| `PENDING_INVALID` | pending file has bad size, magic, reserved bytes, state, sequence, or ID | process fail-stop; no DB write |
| `PENDING_AUTH_FAILED` | pending HMAC mismatch | process fail-stop; no DB write |
| `PENDING_TRANSITION_CONFLICT` | second reserve, wrong expected slot, or old/cleared ID is presented | reject transition; existing reservation unchanged |
| `DB_COMMIT_AUTHORIZATION_MISSING` | startup observes `RESERVED` with any visible target/journal, including promoted WAL or a real pre-mark crash | process fail-stop; no pending upgrade, anchor CAS, or DB write; fresh repair required |
| `ANCHOR_UNAVAILABLE` | key/state/lock/read/fsync backend unavailable | no start; process fail-stop |
| `ANCHOR_CAS_FAILED` | exact expected anchor/pending transition did not CAS | re-read exact files; otherwise process fail-stop |
| `ANCHOR_OVERFLOW` | checked anchor or pending-slot sequence increment fails | process fail-stop |

No failure path decrypts, encrypts, sends, hands off plaintext, clears a
fail-stop, rewrites a tag over untrusted data, or silently re-baselines the
anchor. “Process fail-stop” is an in-memory operational state only; this ADR
does not authorize persisting it into an untrusted SQLite database.

## 10. Compatibility and migration

No released Telegraph client-secret database exists. Version 1 supports only a
fresh exact bootstrap. Every legacy development database—including one whose
old unsigned journal appears stable, one with no journal, or one with an
unkeyed audit chain—returns `MIGRATION_REPAIR_REQUIRED`. Code does not discard,
retag, migrate, or re-baseline it. Recovery requires a fresh protected state,
new device/channel state as applicable, and re-pair. This avoids turning an
unsigned historical target into trusted state.

The exact fresh bootstrap state is the following fixed generation-zero
deterministic-CBOR value; it is not caller-configurable:

```text
genesis_secure_state = {
   0: 1,
   1: null,
   2: [], 3: [], 4: [], 5: [], 6: [], 7: [], 8: [], 9: [],
  10: { 0: 1, 1: bstr32(0x00), 2: 0, 3: 0 },
  11: [],
  12: 0
}

genesis_state_digest = SHA-256(
  "telegraph/rollback-anchor/v1" ||
  deterministic_cbor(genesis_secure_state)
)
```

Key `1=null` is a closed bootstrap sentinel permitted only for this exact
generation-zero value. In every generation greater than zero it must be the
complete ADR 0002 `device_record`; no other field may be null or omitted. Thus
generation zero has no device/account/prekey/pairing/channel/counter/dedup/
receipt/revocation/storage-record row and uses the exact empty audit state from
section 8.1. The SQLite metadata stores client schema version `1`, the
compile-time v1 migration checksum, and the compile-time v1 owned-schema
fingerprint; all three must byte-match the reviewed v1 migration artifact and
freshly recomputed owned schema. No first-run code learns or replaces either
constant from the database.

Fresh bootstrap is the sole anchor-first exception because the target is this
fixed public empty state and contains no ratchet, key record, message, alias,
or handoff.

Bootstrap runs under the stable external lock:

1. require that the configured SQLite database path does not exist and that no
   legacy database, WAL, or shared-memory file exists at that namespace;
2. create and fsync the protected storage-key and anchor-key files with
   `create_new` and OS CSPRNG values;
3. create and verify the exact genesis `EMPTY` pending slot;
4. create and verify external anchor generation zero for the exact empty-state
   digest; and
5. create the v1 SQLite schema in a durable transaction, store the exact empty
   snapshot/schema fingerprint, close/checkpoint as specified by SQLite, fsync
   the database and parent directory, reopen, and recompute byte-for-byte.

The fresh-bootstrap crash matrix is closed:

| Durable artifacts observed at restart | Required action |
|---|---|
| nothing, or stable lock file only | retry fresh bootstrap |
| both valid key files only, no pending/anchor/DB | resume at genesis pending creation |
| both keys plus valid genesis pending, no anchor/DB | resume at generation-zero anchor creation |
| valid keys, genesis pending, generation-zero anchor, no DB | create only the exact empty v1 DB |
| same external set plus exact empty v1 DB | stable bootstrap complete |
| one key without the other; DB without the complete external set; partial/noncanonical DB; non-genesis pending; nonzero anchor; any legacy row/schema; any unknown file combination | `MIGRATION_REPAIR_REQUIRED`; no mutation |

An interrupted temporary file is handled only by the protected atomic-file
rules; it is never parsed as current. After generation zero, device creation is
an ordinary reserved DB-first transition to generation one, creates only an
exact account-v5 payload in outer Account schema 2/version 1 with an empty
canonical alias registry, and emits the
single legal `MIGRATION_BOOTSTRAP/SUCCESS/BOOTSTRAP` event plus
`SECURE_STATE_MUTATION/SUCCESS/PREPARED`. Account payload v4 or an absent/
noncanonical v5 registry at that boundary is `MIGRATION_REPAIR_REQUIRED`.

Fresh install, reopen, creation at every listed crash boundary, migration
checksum, schema fingerprint, corruption, rollback, and namespace-isolation
tests are mandatory. Client-secret bootstrap/migrations must not inspect or
alter relay-opaque tables.

Any future move to Alternative A, any journal/audit key or domain change, any
field/key change, a `K_anchor` rotation protocol, free-form audit detail, a new
record type, or an alternate codec requires a new ADR and independent security
review. Unknown future schemas fail closed; they are not best-effort decoded.

## 11. Required typed APIs and boundaries

The implementation API is closed and typed. Names may follow Rust conventions,
but capability and data flow must be equivalent to this list:

- `AnchorValue`, `ObservedPendingSlot`, `LiveReservedPending`,
  `StartupReservedPending`, `DbCommittedPending`, `ConsumedPending`,
  `DurableTargetProof`, `PreparedJournal`, and `AnchoredJournal` have private
  fields and validate on construction. Callers cannot change a status or
  binding by struct literal.
- `AuditEventCode`, `AuditOutcomeCode`, `AuditDetailCode`, `AuditAliases`,
  `AuditEntryBody`, `AuthenticatedAuditEntry`, and `AuditChainRecord` encode
  only the closed values and combinations from section 8.
- `AuditAliasBinding`, `AuditAliasRegistry`, `AuditAliasMutationBatch`, and
  `ValidatedAuditAlias` expose only the bounded v5 lookup/preflight/batch
  operations in section 8.3. No raw provider or registry byte API is added.
- `BoundedJournalCodec` encodes/decodes only exact journal keys `0..8` with the
  320-byte limit. `BoundedAuditCodec` encodes/decodes only exact audit keys
  `0..12` with the 512-byte limit. Neither exposes a generic CBOR value/map.
- `SecureStateSnapshot` represents either the one exact generation-zero
  bootstrap value from section 10 or the complete ADR 0002 keys `0..12` with a
  non-null device record and sorted typed arrays. `SecureStateEncoder::encode`
  is bounded and canonical; `SecureStateEncoder::digest` applies only exact
  `telegraph/rollback-anchor/v1` domain bytes to that encoding.
- `ProtectedStateBackend::read_anchor()` and `read_pending()` return only fully
  verified typed values or an unavailable/error result. A startup observation
  of `RESERVED` can yield only `StartupReservedPending`, never the live type.
- `reserve_pending(expected_anchor, target_generation, target_digest)` performs
  the closed external CAS and returns a non-cloneable
  `LiveReservedPending`; it chooses the unique transition ID internally.
- `ClientStore::verify_durable_target(live_reserved, successful_commit)` closes
  and durably reopens the store, recomputes the exact target/journal, and
  returns a non-serializable `DurableTargetProof` only in that live execution.
- `mark_db_committed(live_reserved, durable_target_proof)` performs the only
  legal `RESERVED -> DB_COMMITTED` external CAS and returns
  `DbCommittedPending`. No startup/recovery method has this capability.
- `authenticate_prepared_journal(live_reserved)` constructs and tags only the exact
  `PREPARED` journal bound to that current reservation;
  `authenticate_anchored_journal(prepared, consumed, target_anchor)` changes
  only the status and tag after the typed target proofs match.
- `authenticate_audit_entry(previous_chain, legal_entry_body)` constructs and
  tags only the next exact sequence/generation/link using the closed enum and
  alias rules. It cannot tag caller-provided encoded bytes.
- `verify_pending(observed)`,
  `compare_and_swap_anchor(expected, target, db_committed)`,
  `consume_pending(db_committed, target_anchor)`,
  `clear_consumed(consumed, anchored_journal)`, and
  `clear_aborted(startup_or_live_reserved, exact_from_state_proof)` accept only
  the typed capability and complete current binding. `clear_aborted` additionally
  requires exact from-state SQLite, no journal, and old anchor. A
  stale/copied/reconstructed value cannot authorize another transition.
- Journal authentication accepts only a typed unsigned journal whose binding
  equals the supplied current pending capability. Audit authentication accepts
  only a legal typed enum/alias body. There is no `mac(domain, bytes)`, raw-key,
  arbitrary-domain, arbitrary-file, or arbitrary-status API.
- All HMAC comparisons use a constant-time equality implementation. Length,
  canonicality, enum, and state validation occurs before comparison without
  exposing which secret tag byte differed.

This ADR does not add `SecureTransitionJournal` or any other crypto
`RecordType`; it does not reuse `Account`, `Session`, `Channel`, `Dedup`, or
`Prekey` AAD for a journal, audit entry body/tag, or external pending
commitment. The sole alias registry in section 8.3 is typed private account
payload metadata inside the already appropriate `Account` record; it is not a
MACed audit entry. `AccountStateAnchor` remains an account-record consistency
value only. It must not be used as the complete secure-state digest, external
anchor, pending commitment, session anchor, or audit head.

The backend owns protected file descriptors, locking, HMAC use, and transition
ID generation. The SQLite store owns typed journal/audit persistence and the
complete secure-state encoder. Neither side receives the other's unrestricted
authority.

## 12. Performance and resource bounds

- Exactly one journal row and one external pending slot exist per device. The
  journal is at most 320 bytes and the pending file is exactly 160 bytes.
- A normal transition performs one protected pending reserve, one journal HMAC
  for `PREPARED`, one durable target reopen, one pending `DB_COMMITTED` mark,
  one external anchor CAS, one pending consume, one journal HMAC for `ANCHORED`,
  and one pending clear. It adds no journal AEAD, journal nonce, record-key
  derivation, or network operation.
- Each audit event is at most 512 encoded bytes; no more than 16 are emitted in
  one state transition; the detailed ring is at most 10,000 rows; compaction is
  limited to 1,000 rows per maintenance transition.
- Pending/journal validation is O(1). Audit verification is O(N) with
  `N <= 10,000`.
  Secure-state canonicalization is O(S) over explicitly bounded client-state
  tables and must use checked allocation/length arithmetic.
- Alias-registry decode/rebuild is O(A) with `A <= 10,000`. Every rebuild
  performs the checked aggregate formula in section 8.3 over provider,
  inventory, proofs, used IDs, framing, and registry before allocating or
  resealing. The complete v5 plaintext is at most `1,048,576` bytes; the
  10,000-entry physical registry cap is `640,012` bytes and leaves `408,509`
  bytes for all other variable components at that count. A transition batches
  at most 16 alias mutations into one account-v5 rebuild and outer Account
  reseal; lookup-only events do not reseal it.
- The release-size fixture must construct the exact maximum legal
  `account_v5_len = 1,048,576` canonical state and pass it through the
  existing `seal_account_state -> open_account_state -> v5 decode` path. The
  benchmark reports canonical bytes, checked allocations, seal/open/decode
  time, and reseal count; any larger state fails closed with
  `ACCOUNT_V5_SIZE_EXCEEDED` before `seal_account_state`.
- The normal path has one durable SQLite target commit plus durable reopen,
  five fixed-size protected-file state changes (reserve, `DB_COMMITTED`, anchor
  CAS, consume, clear), and one small durable SQLite status commit. No lock is
  held across network I/O.
- T3b must measure the complete state-before-send transition on the release
  target; the existing target is p95 at or below 50 ms excluding network
  latency. A miss is a reported deviation, not permission to weaken fsync,
  journaling, audit, or anchor checks.

These are safety/resource bounds, not production-throughput or availability
claims.

## 13. Acceptance vectors

The implementation gate remains closed until an independent reviewer executes
at least these vectors against the exact committed source and root-locked
dependencies:

1. **P01 pending codec and authentication:** the exact 160-byte genesis and all
   five slot states round-trip byte-equal. Mutating every byte class (including
   magic, reserved bytes, state, sequence, transition ID, either generation,
   either digest, and tag) yields `PENDING_INVALID` or
   `PENDING_AUTH_FAILED`. Tag comparison is exercised with first-, middle-, and
   last-byte mismatches through the constant-time verifier.
2. **P02 pending state machine:** `reserve_pending`, `mark_db_committed`,
   `verify_pending`, `consume_pending`, `clear_consumed`, and the narrow
   `clear_aborted` traverse only section 4.1 edges. A stale or reconstructed
   token, wrong expected anchor, second reserve, skipped state, repeated mark/
   consume/clear, or sequence overflow fails without changing the slot.
3. **P03 startup capability separation:** compile-fail/public-API tests prove
   `read_pending` and startup decode cannot produce `LiveReservedPending` or
   `DurableTargetProof`. Runtime recovery never calls or reaches
   `mark_db_committed`; every observed `RESERVED` plus target/journal returns
   `DB_COMMIT_AUTHORIZATION_MISSING`.
4. **P04 atomic external files:** inject crash/error before and after temporary
   write, file fsync, rename, directory fsync, reopen, and verification for both
   pending and anchor files, including `RESERVED -> DB_COMMITTED`. Restart
   accepts only one complete authenticated old or new file; old `RESERVED` with
   visible target fail-stops rather than being upgraded.
5. **J01 canonical journal:** valid exact keys `0..8` round-trip byte-equal
   within 320 bytes. Every unknown, duplicate, reordered, indefinite,
   non-shortest, wrong-type, wrong-length, over-limit, or trailing mutation
   rejects before an external CAS.
6. **J02 journal tamper and B0 regression:** mutate every journal field and tag
   independently and supply unsigned, unkeyed-hash, or arbitrary-domain
   `PREPARED` fixtures. Each returns `JOURNAL_AUTH_FAILED` or
   `JOURNAL_INVALID`; no fixture causes a pending mark/consume, anchor CAS, DB
   mutation, crypto, output, or handoff.
7. **J03 normal transition:** reservation, successful durable SQLite commit,
   separate reopen and exact target/journal recomputation, durable
   `DB_COMMITTED`, anchor CAS, pending consumption, durable `ANCHORED`, and
   pending clear produce exactly one next generation. Output is ineligible
   until final re-verification.
8. **J04 state `A0` and genuinely uncommitted WAL:** crash after `RESERVED` but
   before SQLite commit. With uncommitted WAL remaining invisible, startup sees
   exact from-state/no journal and may only abort-clear. No generation advances
   and no uncommitted frame becomes trusted.
9. **J05 promoted-uncommitted-WAL attack:** begin writing a valid target and
   authenticated journal, omit a real commit, then alter/restore WAL/page
   material so SQLite presents it as committed. Because pending remains
   `RESERVED`, startup returns `DB_COMMIT_AUTHORIZATION_MISSING`, performs no
   mark or anchor CAS, and leaves DB/WAL/SHM byte-identical.
10. **J06 real commit before pending mark:** let SQLite commit return success
    and verify that target is durable, then crash immediately before or during
    `mark_db_committed` such that the old `RESERVED` file remains. Restart gives
    the same fail-stop/repair-required result as J05. Availability is not
    recovered by inferring the commit.
11. **J07 crash after `DB_COMMITTED`:** exact target SQLite, authenticated
    `PREPARED`, old anchor, and matching `DB_COMMITTED` perform one and only one
    anchor CAS, then consume, mark `ANCHORED`, and clear.
12. **J08 crash after anchor CAS:** exact target SQLite, authenticated
    `PREPARED`, target anchor, and exact `DB_COMMITTED` or `CONSUMED` never
    perform a second anchor CAS; they finish consume/status/clear exactly once.
13. **J09 terminal crash and cleanup matrix:** inject crashes after pending
    consume, after `ANCHORED`, after pending clear, and during journal cleanup.
    Every restart matches only `R2b`, `R3a`, `R3b`, or `S0`; cleanup requires
    the retained exact `CLEARED` commitment.
14. **J10 two authentic tags from one from-state:** construct two authentic
    `PREPARED` rows with the same from generation/digest but distinct IDs and
    targets. Only the live normal flow can mark its current binding
    `DB_COMMITTED`; a second reserve conflicts, and neither startup nor the
    other valid tag can authorize an anchor CAS.
15. **J11 cancelled/cleared resurrection:** reserve then lawfully abort before
    DB commit, clear the slot, and restore authentic stale pages containing the
    old transition's target/journal. Repeat after a successful `CLEARED`
    transition. Both paths fail-stop with no DB write, audit, checkpoint,
    crypto, output, or handoff; DB/WAL/SHM bytes remain unchanged.
16. **J12 closed mismatch matrix:** cross-product old, target, and third
    generations/digests across SQLite, anchor, pending, and journal, including
    all pending states, committed/uncommitted/promoted WAL, absent/duplicate
    journal, non-adjacent generation, and changed digest. Every combination not
    listed in section 5.2 fail-stops before a DB write.
17. **J13 concurrency and ambiguity:** two processes and two threads contend on
    the stable lock and from-state. Exactly one live reservation may win. Every
    commit/lock/read/write/fsync/rename/directory-fsync/reopen uncertainty is
    resolved only by verified exact state; it never mints a replacement live
    proof.
18. **J14 online key rotation is unsupported:** any request to rotate
    `K_storage` or `K_anchor`, including suspected compromise at each boundary,
    returns `SECURE_STATE_REPAIR_REQUIRED`, changes no SQLite/external state,
    sends nothing, and requires fresh state/re-pair. No dual-slot, reseal, or
    old-key-erasure recovery path is accepted.
19. **N01 durable record nonce uniqueness:** a forced duplicate
    `(record_id, record_version, nonce)` returns `RECORD_NONCE_REUSE`, commits
    neither record nor anchor, and does not retry or silently reseal. Restart
    and concurrent-writer variants give the same result.
20. **A01 canonicality, enums, and privacy:** exact keys `0..12` round-trip
    within 512 bytes. Unknown enum values, every unlisted event/outcome/detail
    tuple, every invalid alias-presence pattern, free text, arbitrary blobs,
    plaintext, key, code, thread/workspace, state-digest, protocol-ID, and local
    handle fields are unrepresentable and rejected.
21. **A02 empty and terminal invariants:** generation zero has zero rows,
    all-zero head, watermark zero, and last generation zero. For non-empty
    chains, the final row tag equals the retained head and its anchor generation
    equals `last_generation`, which equals the secure-state anchor generation.
    Mutating any component returns `AUDIT_CHAIN_INVALID`.
22. **A03 audit tamper:** mutation, deletion, insertion, reorder, duplicate or
    skipped sequence, fork, changed previous tag, changed compaction watermark,
    final-head substitution, and row-generation substitution all return
    `AUDIT_CHAIN_INVALID` before a DB write or security action.
23. **A04 atomicity and clock:** injected codec, HMAC, or audit-insert failure
    rolls back the associated security-state mutation. Equal UTC epoch seconds
    succeed; a timestamp one second below the preceding row returns
    `CLOCK_ROLLBACK` without partial state.
24. **A05 account-v5/registry codec and maximum round-trip:** exact empty and
    boundary-max v5 payloads pass the existing
    `seal_account_state -> open_account_state -> v5 decode` path with
    byte-equal canonical round-trip. The boundary fixture is the complete
    canonical plaintext at exactly `account_v5_len = 1,048,576`, including all
    framing, provider, inventory, proofs, used IDs, and registry bytes; it is
    not a registry-only boundary. Mutate every header/length/binding/registry
    field, ordering, uniqueness, reserved byte, trailing byte, or checked-size
    edge; all reject. `1,048,577` and every checked aggregate overflow return
    `ACCOUNT_V5_SIZE_EXCEEDED` before alias randomness, outer nonce generation,
    or reseal. Internal version 4 or outer Account schema 1 in a client DB
    returns `MIGRATION_REPAIR_REQUIRED`, never an automatic rewrite.
25. **A06 alias allocation and collision:** a deterministic CSPRNG fixture
    forces 15 collisions followed by a unique alias, then 16 collisions. The
    first succeeds once; the second returns `RANDOMNESS_FAILURE`. Candidates
    are checked against live, tombstone, and same-batch aliases, and no local/
    protocol key appears in an audit row.
26. **A07 registry capacity/preflight:** a 10,000-entry registry succeeds only
    when the actual complete aggregate satisfies section 8.3 (at most
    `408,509` bytes for the other variable components at that count). Entry
    10,001 or a storage-index-capacity failure returns
    `AUDIT_ALIAS_CAPACITY_EXHAUSTED`; an aggregate overflow or any target whose
    complete canonical v5 plaintext exceeds `1,048,576` returns
    `ACCOUNT_V5_SIZE_EXCEEDED`. Batch 17, failed allocation, record-version
    overflow, and all checked-size arithmetic failures return their exact
    fail-closed code before alias randomness, record nonce generation, reseal,
    or mutation. Exercise both a 10,000-entry success at the legal maximum
    and a 10,000-entry rejection with an oversized base payload.
27. **A08 alias lifecycle:** attempts to delete, decrease retention, tombstone
    with a nonfinal audit sequence, or reuse an alias while a
    live audit/security reference exists return `STATE_INCONSISTENT`. Tombstone
    removal occurs only when the watermark reaches `last_audit_sequence`,
    trusted UTC is strictly greater than the retention deadline, and the owning
    security relationship is removable. Equality at the deadline retains the
    tombstone; no surviving row is attributed to a new colliding alias.
28. **A09 registry update/restart/performance:** lookup-only audit events cause
    zero account rebuilds/reseals. Up to 16 allocations/lifecycle changes in a
    transition cause exactly one v5 rebuild and one outer reseal; provider
    mutation preserves the registry. Cold restart validates AEAD, v5 binding,
    canonical registry, Account record version/digest, and rebuilds the cache.
    Restart the exact `1,048,576`-byte boundary state and require the same
    `seal_account_state -> open_account_state -> v5 decode` byte-equal result;
    a `1,048,577`-byte target fails before seal. A maximum-boundary
    release-target benchmark remains within the section 12 p95 budget and
    reports canonical bytes, component lengths, checked allocations,
    seal/open/decode time, and reseal count.
29. **A10 compaction:** batches never exceed 1,000 and the detailed ring
    converges to at most 10,000 rows. Watermark, predecessor link, head, and
    terminal-generation invariants survive every crash boundary. Replay,
    receipt, invalid-auth budget, revocation, quarantine, record index, and
    rollback fields are untouched.
30. **A11 bounded load and overflow:** 16 legal events in one transition
    succeed; event 17 rejects the entire transition. Checked sequence and
    generation overflow fail-stop with no partial row, slot, journal, or anchor
    mutation.
31. **M01 exact fresh bootstrap:** execute every row of the section 10 crash
    matrix, including old/new atomic-file outcomes. Only the exact empty path,
    both keys, genesis `EMPTY` pending, generation-zero anchor, and exact empty
    v1 DB can resume or complete; partial, noncanonical, unknown, or mixed
    artifact sets return `MIGRATION_REPAIR_REQUIRED` without mutation.
32. **M02 legacy rejection:** databases with no journal, an unsigned or
    apparently stable journal, an unkeyed audit chain, any legacy row/schema,
    account payload v4/outer Account schema 1, or a valid-looking old digest all return
    `MIGRATION_REPAIR_REQUIRED`. Nothing retags, migrates, re-baselines, deletes,
    or activates them.
33. **M03 bootstrap integrity and isolation:** fresh/reopen/schema-checksum/
    schema-fingerprint/corruption/restart tests recompute exact genesis bytes.
    Generation one creates exact account v5 plus empty `T3AR` registry. Relay-
    opaque and unrelated-table sentinels remain byte-identical through all
    success and failure paths.
34. **I01 typed capability boundary:** compile-fail and source-review fixtures
    show callers cannot construct or mutate journal/pending/audit states through
    public fields, pass arbitrary domains or raw HMAC keys, encode unbounded
    generic CBOR, recover a live reservation after restart, or ask the protected
    backend to authenticate arbitrary files.
35. **I02 crypto namespace boundary:** source/dependency scans confirm no new
    crypto `RecordType`; only the exact account-v5 private registry is added.
    Journal, audit entries/tags, and pending state do not reuse record AAD, and
    `AccountStateAnchor` is not used as complete secure-state digest, external
    anchor, pending commitment, session anchor, or audit head.
36. **R4 V12/V13/V15 integration:** outbound data is durably persisted and
    anchored before send eligibility; inbound data is durably persisted and
    anchored before session handoff; replay, receipt, invalid-auth, prekey,
    rotation-required, and verified-bundle state participates in the same
    transition and crash recovery exactly once.
37. **Explicit non-goal vector:** roll back SQLite, external anchor, and
    external pending slot together to a mutually matching authentic old state.
    The fixture documents endpoint compromise outside detection; it must not
    expect a rejection or claim detection, protection, E2EE, or recovery.

All vectors must run single-threaded and at default concurrency, with restart
and corruption fixtures, exact toolchain/commit/SHA evidence, fmt/check/clippy
`-D warnings`, `git diff --check`, and no repository-generated secret or
credential artifact.

## 14. Prohibited claims

Acceptance of this proposal would define only local crash/rollback/audit
persistence behavior under its stated assumptions. It would not prove peer
identity, relay confidentiality, message E2EE, metadata privacy, endpoint
security, production readiness, or resistance to simultaneous rollback of
SQLite, the external anchor, and the external pending commitment. No
implementation or evidence may claim Telegraph E2EE until the separately
authorized protocol, client, integration, threat-model, and independent
release gates have all passed.
