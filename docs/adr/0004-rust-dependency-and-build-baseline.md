# ADR 0004: Rust dependency and build baseline

- Status: Proposed baseline; implementation remains gated by ADR 0002/R4 and ADR 0003
- Date: 2026-08-23
- Decision owner: Telegraph technical lead
- Scope: Rust workspace dependencies, feature policy, build/release settings, and
  test/tooling supply chain
- Security status: design only; E2EE is not implemented or claimed

## Decision disposition and evidence state

This record has three deliberately separate meanings:

- **Design acceptance:** the dependency, Linux storage, CBOR, SQLite, build,
  and packaging choices below are the planning baseline. They close the
  design choice of a concrete small backend; they do not claim that the
  backend exists.
- **Implementation evidence:** as of this research-only revision, no
  Cargo.toml, Cargo.lock, deny.toml, SBOM, feature graph, secure-storage
  fixture, SQLite concurrency test, CBOR fixture/fuzz corpus, or Python lock
  has been generated by this ADR. Those artifacts are T0/T1/T2/T3/T5
  deliverables and must be reported as evidence when generated.
- **Release gate:** no crypto implementation, bridge release, production
  binary, or security claim is authorized until the implementation evidence
  and the independent R4/T8 gates pass. T0 workspace scaffolding and T1
  neutral framing may proceed without the Python tuple or a crypto provider;
  those tasks must not present this ADR as implementation evidence.

## Decision summary

Telegraph uses a small Rust workspace with the dependency direction and trust
boundaries in ADR 0001. The build floor is Rust 1.85 with edition 2024. The
reproducible release toolchain is Rust 1.85.1, while the supported package
floor is expressed as rust-version = 1.85 and is checked separately in CI.
The root Cargo.lock, deny.toml, and SBOM are required future T0/release
artifacts owned and generated by the T0 integration owner. Every release and
security report records the toolchain, target, lockfile revision, feature
graph, license closure, advisory database revision, and SBOM.

The baseline deliberately uses:

- Tokio 1.53.x, Axum 0.8.x, rustls 0.23.x, and tokio-rustls 0.26.x;
- reqwest 0.12.x with rustls-only, manually supplied trust roots;
- rusqlite 0.40.x with bundled SQLite, WAL, explicit transactions, and a
  bounded blocking boundary;
- cbor4ii 1.2.x as a small MIT-licensed, schema-specific CBOR codec;
- the exact vodozemac 0.10.0 release with default features disabled;
- XChaCha20-Poly1305, HKDF-SHA-256, SHA-256, OS CSPRNG, zeroize, and secrecy
  only at the narrow storage/provider boundaries already described by ADR 0002;
- clap 4.6.x and tracing 0.1.x with a minimal subscriber;
- a separately locked Python bridge package, with no Python dependency in the
  Rust graph.

Versions in this ADR are compatibility ranges for manifests, not substitutes
for a lockfile. The patch versions called out below are the versions observed
in the official crates.io records on 2026-08-23. A security-sensitive provider
is exact-pinned; a normal runtime crate is upgraded only through a lockfile
refresh, feature audit, tests, advisory/license review, and an explicit
release record.

This ADR does not authorize implementation, production deployment, or any
security claim. In particular, a passing build, a rustls connection, a
database transaction, or a cryptographic library dependency does not establish
E2EE.

Architecture boundary revision (2026-08-24): consistent with ADR 0001, the
selected lightweight dependency graph keeps `telegraph-crypto` as a
provider/byte-level adapter and does not add an unused
`telegraph-protocol` dependency. The `client` crate explicitly depends on both
`crypto` and `protocol` and composes crypto-produced opaque ciphertext with
the neutral `Envelope`; local plaintext remains on the client endpoint path.
This avoids formal-only dependencies and provider/framing coupling. It does
not change the product scope or authorize T3b, deployment, or an E2EE claim.

## MSRV, edition, and toolchain policy

1. Every workspace package declares edition 2024 and rust-version 1.85. This
   is required by the pinned vodozemac 0.10.0 manifest, which declares edition
   2024 and Rust 1.85. The workspace must not silently lower the floor for a
   convenience dependency.
2. rust-toolchain.toml selects the exact stable toolchain 1.85.1 with the
   minimal profile and only the targets/components needed by the repository
   (at least rustfmt and clippy in CI). It must not select nightly for release
   builds or silently auto-update a channel.
3. CI has a floor job on Rust 1.85.1 and a separately named release job using
   the same toolchain and target recorded in the release evidence. A later
   stable toolchain may be used for an explicit compatibility watch job, but
   it does not change the supported floor.
4. The normal gates are cargo fmt --check, cargo check --workspace --locked,
   cargo test --workspace --locked, cargo clippy --workspace --all-targets
   --locked, cargo deny check, and cargo audit. The lockfile must be clean
   before and after every gate.
5. Fuzzing is isolated to a separately pinned nightly runner because
   cargo-fuzz requires nightly instrumentation. Nightly is not a supported
   package or release toolchain and no nightly-only API may enter production
   crates.
6. Cargo.lock is checked in even when the workspace contains libraries. T0 is
   the only lockfile integration owner named by ADR 0001 and the task
   breakdown. A task branch proposes manifest changes; T0 regenerates and
   audits the lock after merge. Release and CI commands use --locked.
7. A dependency whose declared MSRV is above 1.85 is not accepted into a
   production target. A test/tooling binary may run in a separate newer
   environment only when its exact toolchain is recorded and it cannot alter
   the production lock or release artifact.

The edition and MSRV fields are Cargo metadata, not a claim that all
transitive crates support every target. The floor job must build each declared
release target and report any target-specific exception.

## Build and profile baseline

The workspace profile is intentionally conservative and measurable:

- release: opt-level 3, thin LTO, one codegen unit, symbol stripping, panic
  unwind, and overflow checks enabled;
- dev and test: overflow checks enabled and normal debug assertions;
- no release debug information unless a separately named diagnostic artifact is
  requested;
- no build script may download source, execute a network command, or select a
  native crypto/database provider outside the locked graph.

The release profile settings are a decision baseline, not a promise about
binary size. Thin LTO is the default trade-off between code size/startup and
build time. Panic unwind is intentional so Drop-based cleanup, including
zeroize guards, gets a chance to run; it is not a recovery mechanism for
secret state. No secret path may depend on panic recovery, and normal errors
must return a fail-closed Result. A future relay panic=abort profile requires
an independent review of cleanup and crash semantics. Changing LTO, removing
overflow checks, changing panic strategy, or disabling symbol stripping
requires measured release evidence.

Reproducible build evidence records rustc -Vv, cargo -V, target triple,
Cargo.lock checksum, enabled features, source revision, build profile, and
the release environment. Release artifacts are produced from a clean checkout
with no credentials, relay address, or local path embedded.

## Dependency direction and feature rules

The dependency graph follows ADR 0001:

- protocol has no Tokio, network, database, Codex, or crypto-provider edge;
- crypto depends only on the approved vodozemac adapter and its narrow
  reviewed crypto/storage dependencies; it remains provider/byte-level and
  does not depend on protocol framing;
- store has separate relay-opaque and client-secret paths, does not interpret
  plaintext, and never accepts provider session state in its relay-opaque
  path;
- relay depends on protocol and relay-opaque store state and never sees
  plaintext, private keys, or provider session state;
- client depends on protocol, crypto, and local store. It owns transport,
  channel state, the crypto-to-Envelope composition, and the local bridge
  boundary;
- cli owns user interaction and does not bypass client state;
- the Python bridge is a process/package boundary, not a Rust generic IR.

The dependency graph is a real API boundary, not a checklist target: no
unused dependency may be introduced solely to satisfy a nominal edge. Protocol
tests own canonical framing; crypto tests own provider/byte-level invariants;
client tests must cover the actual crypto-to-Envelope composition and local
handoff; relay/store tests must remain opaque and reject plaintext/provider
session inputs. Any future change that makes crypto consume protocol types
requires a reviewed ADR update and a manifest/feature-graph review.

Feature policy:

- Every direct dependency is written with default-features = false unless a
  table below explicitly names the required default-free feature set.
- A new feature requires a reason, owner, target crate, expected transitive
  packages, and a feature-graph diff.
- cargo tree -e features --workspace --all-targets is attached to the release
  evidence. The graph must show no native-tls, openssl, aws-lc-rs, SQLCipher,
  WebSocket, multipart, or unreviewed default feature.
- Protocol wire fields are not derived from a general-purpose serialization
  model. The wire wrapper has exact integer keys, bounded lengths, strict
  duplicate/unknown-field rejection, and canonical-byte tests.
- No dependency may introduce a generic intermediate representation, a
  cross-harness control plane, or an implicit shared runtime.

## Canonical CBOR strategy

ADR 0001/0002 require compact integer-keyed CBOR and RFC 8949 deterministic
transcript bytes. The selected implementation is cbor4ii 1.2.x core with
schema-specific Encode/Decode implementations. cbor4ii 1.2.2 is MIT
licensed. Protocol and general Telegraph wire paths request no `serde1`,
`use_alloc`, or `use_std` feature. When `telegraph-crypto` is integrated,
[ADR 0005](0005-provider-pickle-cbor4ii-serde1-exception.md) permits only its
private provider-state dependency edge to request `serde1`; Cargo's unified
resolved package feature set is exactly `{serde, serde1, use_alloc}`, while
`use_std` remains forbidden. This is a repository-policy boundary, not crate
feature isolation, so non-crypto source may not use `cbor4ii::serde`. The
codec's generic facilities are not treated as a canonicality proof.

For every security-sensitive object:

1. The schema constructor writes a definite-length map with the exact expected
   integer keys in strictly ascending encoded-key order. A duplicate or
   out-of-order key is an error, not a value to be normalized.
2. The decoder accepts only the fixed schema: known key, exact CBOR major
   type, exact or bounded length, and the ADR 0002 field constraints. Floats,
   tags, negative integers, indefinite-length maps/arrays/strings, unknown
   keys, duplicate keys, and oversized values are rejected.
3. The decoder consumes exactly all input bytes. It rejects trailing bytes,
   non-shortest integer or length encodings, and any representation whose
   fixed-schema re-encoding is not byte-for-byte equal to the received bytes.
   Re-encoding is performed by the same schema-specific constructor, not by
   a generic map sorter.
4. Fixtures cover every approved object, canonical-byte equality, wrong key
   order, duplicate/unknown keys, non-shortest integers/lengths, indefinite
   items, float/tag values, truncation, trailing bytes, and one byte over each
   size limit. Bounded property and fuzz tests exercise the decoder before
   any crypto, allocation proportional to attacker input, or database work.
5. Relay code validates only bounded opaque outer framing and never decodes
   ciphertext into a plaintext model.

This is a schema-specific canonical strategy, not a claim that cbor4ii
automatically canonicalizes arbitrary values. minicbor 2.3.0 remains a
possible equivalent small codec, but its official crates.io license is
BlueOak-1.0.0 rather than MIT/Apache-2.0 and therefore needs a separate legal
allowlist decision. Ciborium is removed from the security-sensitive baseline;
it may not be reintroduced as a canonicality shortcut. Any codec replacement
requires identical fixtures, bounded decoding, license closure, and an ADR
update before implementation.

## SQLite and blocking isolation

rusqlite is synchronous by design. The relay must never run a connection,
transaction, checkpoint, migration, or backup directly on a Tokio request
worker. One dedicated blocking writer actor owns the only writable connection
and the only write queue. The writer queue capacity is 64 operations; an
admission attempt when it is full returns a bounded backpressure result and
the HTTP layer returns 503 with a bounded Retry-After, rather than spawning a
task or growing memory. No other module may open a writable connection.

Read-only work uses at most eight SQLite read connections behind a Tokio
semaphore of eight permits. There is no unbounded read queue: failure to
obtain a permit within 25 ms returns 503/backpressure. Each normal database
operation has a 250 ms end-to-end blocking deadline and a 100 ms SQLite busy
timeout. Maintenance operations (checkpoint, expiry, migration, backup) run
in a separate bounded maintenance lane with an explicit 2 s deadline and are
not admitted from request handlers.

Request cancellation is checked before queue admission and while awaiting a
permit. A queued operation can be removed before it starts. Once a SQLite
transaction has begun, cancellation stops waiting but does not interrupt the
connection in the middle of a transaction; the writer commits or rolls back
within the deadline and reports the result to the audit path. Busy timeout,
blocking timeout, queue-full, read-permit timeout, and client disconnect are
separate bounded metrics/error classes. The API never retries a timed-out
write blindly and never turns a 503 into an unbounded local retry loop.

WAL mode, busy timeout, bounded row/body sizes, indexes, checkpoint policy,
expiry/tombstone transitions, and crash tests remain the ADR 0001/T2 contract.
Tests must fill the writer queue, exhaust eight read permits, cancel before
and after transaction start, force SQLITE_BUSY, restart through WAL recovery,
and prove no task/queue/connection grows without a bound. The measured
100-write plus 100-read/s target is evaluated with these same limits.

The bundled feature is selected to avoid a host SQLite ABI and to make the
SQLite source part of the locked build. This is not a license or security
claim about SQLite. The build must still record SQLite amalgamation version
and license data in the SBOM. SQLCipher and any feature that pulls
vendored OpenSSL are prohibited.

## Linux MVP secure storage and rollback anchor

The concrete secure-storage choice for the Linux MVP is a protected-file
adapter, not a hardware-backed credential store. The relay/client daemon is
installed as a dedicated root-owned Linux service for this MVP. If the
deployment is not able to enforce the owner, mode, lock, and fsync contract
below, it fails closed rather than relaxing the contract.

The SQLite state directory and the following files are separate configured
locations. The exact deployment path is operator configuration and is not
committed:

- storage-key file: random 32-byte K_storage_master;
- anchor-key file: random 32-byte K_anchor;
- anchor-state file: independent generation, digest, and HMAC record.
- anchor-lock file: a stable sidecar inode used only for the OS file lock, so
  replacing anchor-state cannot accidentally replace the inode being locked.

All four files are regular files owned by UID 0 with mode 0600; their parent
directories are owned by UID 0 with mode 0700. They are not symlinks, are not
inside the SQLite state directory, and are never included in a database
backup. Creation uses create_new and fixed-size records; existing files are
opened only after owner/mode/regular-file checks. Missing, malformed,
unexpectedly sized, wrong-owner, wrong-mode, symlinked, or inaccessible files
fail closed and require device recovery/re-pair. This is an OS-permission
boundary, not hardware-backed protection and not protection against a
compromised root account.

The anchor-state record is fixed-width and contains a schema/version,
anchor_generation, state_digest, and tag. The tag is
HMAC-SHA-256(K_anchor, domain || schema || anchor_generation ||
state_digest). The canonical secure state and digest are the complete state
specified by ADR 0002, not merely a list of table names. K_storage_master and
K_anchor are generated only with the OS CSPRNG; neither key is stored in
SQLite or in the anchor-state file.

One daemon writer owns the anchor state. Before a CAS it takes an exclusive OS
file lock on the stable anchor-lock sidecar using fs2 0.4.x and holds that
lock across the complete operation. The lock sidecar is never renamed:

1. read and validate the current generation, digest, and HMAC;
2. compare both expected generation and expected digest with the proposed
   transition; a mismatch is a CAS failure and never a merge;
3. write the next fixed record to a same-directory root-owned 0600 temporary
   file, write all bytes, and call sync_all/fsync;
4. atomically rename the temporary file over the anchor-state file;
5. open and fsync the parent directory, then re-open and verify the new
   generation, digest, and HMAC.

This is a logical compare-and-swap across the independently locked anchor
file. It is not an atomic multi-resource CAS with SQLite. The DB-first
PREPARED -> anchor CAS -> ANCHORED/COMMITTED sequence in ADR 0002 remains
mandatory. A failed lock, owner/mode check, read, HMAC, fsync, rename,
directory fsync, post-write verification, or generation comparison
quarantines the store and blocks production startup; no code guesses or
reconstructs state from ciphertext.

The lock is a single-daemon-writer invariant, not a claim that advisory locks
defeat a malicious root process. Simultaneous rollback of both SQLite and the
external anchor, or an endpoint/root compromise that controls both, is an
explicit non-goal and must not be described as detectable. A future Windows
credential-store implementation is an adapter decision outside this Linux
MVP; it cannot be inferred from this file backend.

fs2 0.4.3 (MIT OR Apache-2.0, no optional features) is selected for the small
file-lock API. rustix 1.1.x (Apache-2.0 WITH LLVM-exception OR Apache-2.0 OR
MIT) was evaluated but is a broader syscall surface than this MVP needs;
std plus direct libc was not selected because it would move platform-specific
locking and unsafe ABI handling into Telegraph. A future change to rustix,
libc, a privileged helper, a Linux keyring, or a Windows credential store
requires a new adapter review and the same owner/mode/lock/fsync/CAS tests.

## Local cryptographic storage boundary

The only direct primitive composition authorized by this ADR is the
ADR 0002 storage-record construction:

- vodozemac owns Olm channel operations and its internal ratchet;
- XChaCha20-Poly1305 protects serialized account/session records locally;
- HKDF with SHA-256 derives per-record storage keys from the OS-held master;
- getrandom obtains nonces and identity/prekey material from the OS CSPRNG;
- zeroize and secrecy constrain local handling and diagnostics.

The relay never receives these storage keys, private prekeys, pickles,
plaintext, or provider state. No dependency may expose a root key, invent a
confirmation MAC, replace the reviewed Olm profile, or turn storage
encryption into a claim of end-to-end transport security.

## Python bridge packaging

ADR 0003 remains the sole Codex route. Packaging is a separate, locked
artifact:

- The exact Python/SDK/runtime tuple is a T5 gate, not a prerequisite for T0
  workspace scaffolding or T1 neutral framing. It does block T5 acceptance,
  bridge release, and the overall release gate.
- bridge/pyproject.toml uses the standard PEP 621 project metadata and declares
  Python >=3.10, but each supported release pins an exact Python patch,
  stable openai-codex version, and matching published runtime tuple.
- The exact SDK/runtime tuple is intentionally not invented here because the
  official SDK and its bundled runtime are moving. Before T5 acceptance, T5
  must generate a requirements lock with hashes (or an equivalently
  hash-checked lock), record the exact Python/SDK/runtime versions and
  licenses, install it in an isolated environment, and pass a real local
  start/resume/final-response smoke test plus the fake-bridge suite. The
  lock, wheel hashes, runtime evidence, and rollback candidate belong in the
  release SBOM/evidence.
- Install from that hash-checked lock. Do not use a floating latest,
  prerelease, arbitrary codex_bin, or an unpinned runtime.
- The bridge exposes only ADR 0003 restricted JSONL over inherited stdio.
  It never invokes the experimental App Server CLI directly, exposes a
  socket/WebSocket/MCP listener, or accepts caller-controlled cwd, command,
  tool, model, approval, file, or credential fields.
- openai-codex is Apache-2.0 according to the ADR 0003 official repository
  evidence. Every matching runtime and transitive package must be checked
  independently before release; the Python bridge may see local plaintext,
  while the relay must not.

No Python package is a Cargo runtime dependency. Any direct Rust
`serde_json` dependency/use is limited to the reviewed local JSONL bridge
boundary and does not create a generic intermediate representation. The
unavoidable vodozemac-transitive `serde_json` remains provider closure only;
Telegraph code does not call it or expose its values in wire, relay, or
storage formats.

| cargo-audit | 0.21.x (0.21.2) | Apache-2.0 OR MIT | RustSec advisory scan. The newer 0.22.2 line observed on crates.io requires Rust 1.88, so use a separately pinned compatible tool or isolated newer runner. |
| cargo-deny | 0.18.x (0.18.3) | MIT OR Apache-2.0 | License, advisory, bans, and source checks. The newer 0.20.2 line observed on crates.io requires Rust 1.88. |
| cargo-cyclonedx | 0.5.x (0.5.9) | Apache-2.0 | Generate a CycloneDX SBOM from the locked Cargo graph. |
| cargo-auditable | 0.7.x (0.7.5) | MIT OR Apache-2.0 | Optional embedded package/build metadata in release binaries; it complements, not replaces, the external SBOM. |

Built-in Cargo format/check/test/clippy commands remain preferred over adding
test runners or assertion/mocking frameworks. A new test-only crate still
needs the same license, source, advisory, feature, MSRV, and dependency-weight
review.

## Cargo.lock, deny, audit, sources, and SBOM

Cargo.toml, Cargo.lock, deny.toml, audit output, and SBOM are future T0/release
evidence, not evidence already present in this research-only repository. Their
absence does not block T0 workspace scaffolding or T1 neutral framing. Until
T0 generates and an independent reviewer checks them, crypto implementation
and any release artifact remain unauthorized.

Once generated, the checked-in lockfile is the authoritative resolved graph. A
release is blocked when Cargo.lock is absent, dirty, regenerated without a
manifest change, or different between build and audit. Cargo's official
metadata is exported with cargo metadata --locked --format-version 1 and
retained with the release evidence.

deny.toml enforces the following policy:

- licenses: allow only MIT, Apache-2.0, ISC, BSD-2-Clause, BSD-3-Clause,
  Unicode-3.0, Zlib, and CC0-1.0 when the exact component's notices are
  preserved; deny unlicensed and copyleft expressions; deny unknown
  expressions; require a documented owner/expiry for every exception;
- advisories: use the official RustSec advisory database; fail on an
  unignored vulnerability, yanked package, or unresolved high/critical
  advisory; an ignored advisory requires an ADR entry, affected version
  range, impact analysis, owner, expiry, and compensating test;
- sources: allow the crates.io registry only for third-party packages and
  workspace path packages; deny unknown registries and git dependencies in
  release builds unless a reviewed immutable source commit and license
  record are added to an ADR;
- bans: deny openssl, openssl-sys, native-tls, libgit2-sys, SQLCipher
  variants, diesel, sea-orm, sqlx, rdkafka, redis, ethers, alloy, web3,
  WebSocket/remote-control bridge crates, and any generic IR/control-plane
  package; warn on duplicate versions and deny wildcard dependencies.

The source ban is a graph property, not only a direct-manifest rule. CI runs
cargo tree checks and fails if a transitive feature reintroduces a banned
package. A source or license exception never silently widens the runtime
feature set.

Each release publishes:

1. the binary and exact Cargo.lock;
2. a CycloneDX SBOM generated by the pinned cargo-cyclonedx tool from the
   locked graph, plus the Python lock closure. The SBOM/build evidence names
   the bundled SQLite amalgamation version and license;
3. cargo metadata, cargo tree feature output, cargo-deny license/advisory/
   source reports, and cargo-audit output;
4. a feature-graph proof that the artifact has no OpenSSL/native-tls path, no
   forbidden provider/ORM/queue/Web3 package, and the exact vodozemac feature
   set;
5. the measured dependency-weight count and binary/closure delta against the
   prior reviewed baseline;
6. the tool versions, RustSec database revision/date, source revision,
   target, and checksums.

SBOM and audit artifacts are evidence about the dependency closure. They do
not certify cryptographic correctness, E2EE, endpoint safety, or production
readiness.

## Dependency-weight and feature budget

The budget is a gate to keep the MVP small; it is not an unmeasured
performance claim:

- No dependency-weight count exists yet because the workspace manifests and
  lock are future T0 artifacts. T0 must establish the first reviewed baseline
  from Cargo.lock and cargo tree, and every later release must publish the
  delta; this ADR does not imply that the budget has already passed.
- no boundary crate has more than eight direct third-party runtime
  dependencies without a new ADR; protocol should remain at four or fewer;
- the normal production graph (cargo tree --edges normal --no-dev) should
  remain at or below 180 unique third-party packages, and all-targets
  including test/bench tooling at or below 260; the release evidence records
  the exact count and largest additions;
- no single feature may add a native TLS, system proxy, SQLCipher, WebSocket,
  compression, filesystem, or process subtree without an owner and measured
  reason; Tokio process is the only planned exception and is bridge-only;
- default features must be disabled for the tabled direct dependencies unless
  the table explicitly lists them; a feature audit must show no accidental
  aws-lc-rs, native-tls, openssl, or SQLCipher path;
- a dependency graph or binary-size increase above 10 percent over the last
  release baseline requires a diff explaining the new packages, features,
  licenses, advisories, and measured benefit.

If a required supported target cannot meet the budget, the team records the
deviation and a measured alternative; it does not add a distributed service,
ORM, queue, or broad protocol to hide the cost.

## Performance and benchmark budget

The release performance job reuses the targets in ADR 0001 and ADR 0003:

- relay-a on two vCPUs/2 GB with SQLite WAL and 65,536-byte ciphertext:
  100 writes plus 100 reads per second, p95 opaque enqueue/fetch service time
  at or below 100 ms and p99 at or below 250 ms, with bounded queues;
- client state-before-send transition p95 at or below 50 ms excluding
  network latency;
- idle client RSS at or below 64 MiB and idle relay RSS at or below 256 MiB;
- warm bridge JSONL control overhead p95 at or below 5 ms and p99 at or below
  20 ms, bridge startup p95 at or below 3 s, and bridge RSS limits from
  ADR 0003.

The benchmark job has a fixed two-vCPU/2-GB profile, bounded request bodies and
queues, a bounded wall-clock run (no unbounded load generator), and a release
artifact containing warm-up/method, sample count, hardware, toolchain,
throughput, p50/p95/p99, RSS, and queue bounds. Criterion microbenchmarks
cover canonical CBOR, bounded decode/reject, storage-record AEAD, and state
serialization; they do not infer network or Codex latency. A target miss is a
release deviation requiring profiling or an ADR, not permission to switch to
WebSocket, OpenSSL, Redis, Kafka, or a generic IR.

## Rejected and deferred dependencies

- OpenSSL/native-tls: FFI/provider and platform ABI surface; reqwest and the
  relay use rustls only.
- rustls default aws-lc-rs provider: larger native/provider subtree than the
  selected ring feature for this baseline; adoption would require a measured
  target and independent review.
- Diesel, SeaORM, SQLx, PostgreSQL clients, Kafka, and Redis: unnecessary ORM,
  service, or async-driver surface for one SQLite WAL relay; a future backend
  requires a new ADR and measured load need.
- SQLCipher, bundled-sqlcipher-vendored-openssl, and loadable SQLite
  extensions: not part of the relay-opaque store boundary and may reintroduce
  forbidden native crypto.
- ciborium: its CanonicalValue ordering is not accepted as an automatic
  deterministic-wire guarantee; it is removed from the security-sensitive
  baseline rather than used as a canonicality shortcut.
- rustix 1.1.x and direct std+libc locking: rustix is a broader syscall surface
  than this Linux MVP needs, while direct libc would move unsafe,
  platform-specific locking semantics into Telegraph. fs2 is the small
  selected locking adapter.
- Web3/blockchain/wallet/ethers/alloy/web3 crates, MCP/WebSocket/remote
  control, and generic IR crates: outside the two equal text-peer contract.
- vodozemac default libolm compatibility, experimental session configuration,
  low-level APIs, and JavaScript features: outside ADR 0002's reviewed
  baseline.
- minicbor 2.3.x: held as a possible future codec only after BlueOak license
  approval; cbor4ii is the current MIT-licensed schema-specific choice.
- Broad JSON/protobuf models, compression, image/file/attachment stacks, and
  CLI frameworks with arbitrary command/tool execution: larger attack surface
  and outside the protocol/bridge contract.

## Acceptance and claims policy

Design acceptance of this ADR does not block T0 workspace scaffolding or T1
neutral framing. It does block crypto implementation and release until the
future T0 dependency evidence and the following owner-specific evidence have
been generated and reviewed:

- T0 generates the workspace Cargo.toml files, rust-toolchain.toml,
  Cargo.lock, deny.toml, feature graph, license/source/advisory reports,
  dependency-weight baseline, and SBOM. These are not present evidence merely
  because this ADR names their required contents.
- T1 produces cbor4ii schema fixtures and bounded fuzz/property evidence:
  expected integer-key maps are definite-length, strictly increasing and
  unique; all forbidden types/encodings, trailing bytes, and over-limit
  values reject; decode then fixed-schema re-encode is byte-equal.
- T2/T3 produce Linux secure-storage evidence for root-owned 0600 files
  outside SQLite, regular-file/no-symlink and owner/mode checks, fs2 lock
  contention, fixed-record HMAC verification, temp-write fsync, atomic rename,
  parent-directory fsync, logical CAS mismatch, crash recovery, and startup
  fail-closed behavior. The evidence must state that root compromise and
  simultaneous DB+anchor rollback are non-goals and must not claim hardware
  backing or multi-resource atomic CAS.
- T2 produces SQLite evidence for one writer and capacity-64 queue, at most
  eight read permits/connections, 100 ms busy timeout, 250 ms operation
  deadline, cancellation before/after transaction start, queue/permit
  exhaustion, bounded 503/backpressure, WAL restart recovery, and no
  unbounded task/connection growth.
- T5 produces the exact Python requirements lock with package/runtime hashes
  and licenses, then passes isolated install, runtime version, local
  start/resume/final-response smoke, fake bridge, and rollback evidence. This
  gate is specific to T5 and release; it does not block T0/T1.

Before any implementation claim, T0/T1/T2/T3/T4/T5 must attach:

- clean MSRV/edition/toolchain and locked workspace checks;
- the direct and transitive feature graph, dependency-weight count, license
  and source report, RustSec audit, and SBOM;
- canonical-CBOR, SQLite WAL/blocking, storage-record, and bridge packaging
  tests appropriate to the owning task;
- release profile and benchmark evidence with the exact hardware/toolchain;
- a changed-file list and any unresolved ADR 0002/R4/ADR 0003 gate.

The feature audit acceptance command is cargo tree -e features --workspace
--all-targets followed by cargo deny check and cargo audit. It must prove:
rustls-only transport, no OpenSSL/native-tls, no SQLCipher/ORM/Kafka/Redis/
Web3/generic IR, vodozemac default-features=false, and cbor4ii's
schema-specific bounded CBOR path. Under ADR 0005 C1 it must additionally
prove that only the crypto provider-state edge directly requests `serde1`,
that the unified resolved cbor4ii feature set is exactly
`{serde, serde1, use_alloc}`, and that `use_std` is absent; this is policy
enforcement, not crate feature isolation. It must also prove the fs2 Linux
adapter's exact feature/license closure, the bundled SQLite version/license in
the SBOM, and no secret/plaintext path to relay code. It must publish the
dependency-weight count and delta; no current count is implied by this ADR.

The release gate is closed until all of the above evidence is present,
reviewed, reproducible from a clean checkout, and reconciled with ADR 0002,
ADR 0003, R4, and T8. In particular, a generated Cargo.lock, passing audit,
or green scaffold build is implementation evidence only; it does not by
itself authorize crypto, a bridge release, production, or a security claim.

None of these checks establishes E2EE, an authenticated peer, metadata
privacy, availability, arbitrary existing-TUI attachment, or independent
security-review approval. Those claims remain prohibited until the evidence
and gates named by ADR 0001, ADR 0002, ADR 0003, and T8 are closed.
